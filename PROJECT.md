# Мониторинг Maxval

## Статус проекта

- Текущая рабочая версия: `0.8.5`.
- Опорный (якорный) релиз: `0.8.5`.
- Текущая ревизия Alembic: `0036`.
- Рабочая установка содержит сохраняемые данные. Обычное обновление не должно удалять
  PostgreSQL volume, площадки, объекты, пользователей, настройки или историю.
- Конфигурационные и полные резервные копии восстанавливаются только при точном
  совпадении версии приложения.
- Этот файл и документация описывают только действующее состояние 0.8.5.

## Назначение

Monitoring Maxval — компактная внутренняя система контроля доступности серверов,
компьютеров, сетевых узлов, камер, сайтов и сервисов. Основной сценарий — локальная
сеть или VPN, около 255 объектов, типовой интервал проверки пять минут.

## Граница продукта

**Проект не является аналогом Zabbix.**

Не планируются универсальный сбор произвольных метрик, язык выражений, сложные цепочки
триггеров, автоматическое обнаружение всей сети и тяжёлый редактор топологии. Новая
сложность добавляется только под подтверждённую практическую задачу. Windows-агенты и
массовый сбор показателей рабочих станций не относятся к текущему этапу.

## Актуальные возможности

- площадки, недельные графики работы и сохраняемый ручной порядок;
- одна опциональная точка входа площадки типа «Сеть» или «Сервер»: её primary DOWN
  временно подавляет каскадный polling объектов этой площадки без synthetic results и
  дочерних incidents;
- объекты с основной TCP, HTTP, HTTPS, ICMP или RTSP-проверкой и дополнительными
  TCP, HTTP, HTTPS, ICMP, RTSP, DNS A/AAAA или контролем свежести каталога;
  одна основная проверка определяет availability, а именованные сервисные проверки имеют
  собственную историю и инциденты; HTTP/HTTPS-сервисы могут дополнительно проверять
  точный код, наличие/отсутствие текста, максимальное время ответа и, только для HTTPS,
  срок сертификата;
- опциональная SNMP v1/v2c-телеметрия объектов: System OID, ручные OID и ограниченные
  производные формулы по OID, числовая история,
  базовая IF-MIB-инвентаризация, текущие RX/TX интерфейсов, история SNMP-графиков,
  Printer-MIB расходники и UPS-MIB (RFC 1628) для батареи, питания и нагрузки;
- плановый и защищённый ручной опрос, ограничение параллелизма и история результатов;
- текущие состояния, избранные объекты, фильтры, сортировка, пагинация и автообновление;
- безопасное копирование объекта с его вторичными сервисами и SNMP-конфигурацией без
  переноса результатов, истории, incidents и другого runtime-состояния;
- подтверждённые инциденты, восстановления, отчёты доступности и графики задержки;
- информационная плашка «Нестабильная связь» после краткого неподтверждённого сбоя:
  она не создаёт incident, не меняет health и исчезает через час без новых событий;
- показатели Linux-сервера портала без отдельного агента;
- локальные пользователи, роли `admin`/`viewer`, Argon2id, серверные сессии, CSRF,
  защита входа от перебора и аудит;
- внутренний чат, центр оповещений, SMTP и PWA Push;
- подавление Push сообщения, если получатель действительно смотрит открытый диалог;
- конфигурационные и полные резервные копии с проверкой целостности;
- адаптивный интерфейс, светлая/тёмная тема и фоновое сохранение основных форм;
- Docker Compose для Linux.

## HTTP, HTTPS и PWA

- HTTP на порту `8000` остаётся режимом по умолчанию и доступен в локальной сети.
- HTTPS опционален и обслуживается отдельным Caddy; приложение внутри Docker-сети
  продолжает работать по HTTP.
- HTTPS и redirect HTTP → HTTPS включаются независимо. Redirect использует `307`, HSTS
  не применяется.
- TLS-manager не имеет Docker socket. Он проверяет candidate certificate/private key,
  активирует пару только после успешной проверки Caddy и хранит последнюю рабочую пару
  для rollback.
- Сертификаты и private keys находятся вне БД. Можно загрузить собственную пару или
  создать внутренний CA и серверный сертификат; интерфейс выдаёт только публичный CA.
- При истёкшем сертификате или остатке не более двух суток redirect автоматически
  отключается. Его ручное включение блокируется, а администраторы получают оповещение.
- Срок предварительного предупреждения о сертификате настраивается отдельно.
- PWA включает manifest, иконки, service worker, Push и безопасную offline-страницу.
  Динамические данные мониторинга не выдаются из устаревшего cache.

Подробные утверждённые решения находятся в
[`docs/decisions/https-pwa.md`](docs/decisions/https-pwa.md).

## Данные и обновления

- PostgreSQL — основное хранилище; SQLAlchemy — слой доступа; Alembic — единственный
  способ изменения рабочей схемы.
- Перед обновлением создаётся и проверяется резервная копия.
- При штатном обновлении сохраняются рабочий `.env`, PostgreSQL volume, backup volume и
  каталог `tls/`.
- `docker compose down -v` запрещён для обычного обновления: `-v` удаляет данные.
- Новый `.env` из релизного ZIP предназначен для чистой установки. Он не должен
  автоматически заменять рабочий `.env` существующей системы.
- Реальные пароли, private keys, адреса и персональные данные не хранятся в репозитории
  и документации.

## Архитектурные принципы

- Один модуль — одна ответственность; веб, модели, проверки, планировщик, инциденты,
  уведомления, TLS и хранение разделены.
- Состояние объекта вычисляется единообразно и используется интерфейсом, инцидентами,
  уведомлениями и отчётами.
- Интерфейс остаётся серверным: FastAPI, Jinja2, собственные CSS и JavaScript.
- Изменяющие действия имеют серверную авторизацию и CSRF-защиту; основные динамические
  формы сохраняют рабочий сценарий без JavaScript.
- Встроенный планировщик запускается только в одном процессе приложения.
- Масштабирование, отдельный worker и филиальные коллекторы вводятся только при
  подтверждённой необходимости.
