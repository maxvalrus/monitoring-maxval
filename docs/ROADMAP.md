# Roadmap «Мониторинг Maxval»

В этом документе находятся только незавершённые планы. Выполненные изменения вынесены
в [`CHANGELOG.md`](../CHANGELOG.md) и [`docs/releases/`](releases/).

## Текущее состояние

- Рабочая версия: `0.8.5`.
- Опорный (якорный) релиз: `0.8.5`.
- Текущая работа: UPS-MIB RFC 1628 и APC PowerNet реализованы; специализированная
  страница объединяет актуальные данные и историю. Реализованы ограниченные производные
  SNMP-метрики по OID, включая нормализацию памяти HOST-RESOURCES-MIB. Точка входа площадки, расширенные
  HTTP/HTTPS-проверки и мониторинг TLS-сертификатов стабилизированы.
- SNMP v1/v2c Core, базовая IF-MIB-инвентаризация, текущие RX/TX-счётчики, история
  интерфейсов и пороги Warning/Critical реализованы. SNMP v3, traps и сетевое
  discovery не добавляются автоматически.
- Новый релиз не собирается без прямой команды пользователя с номером версии.
- Для чистой установки и безопасного fast-forward обновления приватного GitHub-клона
  добавлены интерактивные скрипты; они не заменяют release ZIP и не меняют модель
  данных. Решение описано в `docs/decisions/github-installers.md`.

## Согласованный порядок дальнейшей разработки

Каждая функция проходит отдельный этап: проектирование, реализация, ручной тест,
адресные правки и стабилизация. Новая функция не начинается до завершения предыдущей.
Релиз и повышение версии выполняются только по прямой команде пользователя.

1. **Зависимости объектов.** Расширить реализованную точку входа площадки только при
   подтверждённой необходимости: роутер, VPN или другой родитель и подавление каскадных
   инцидентов дочерних объектов.
2. **Flapping detection.** Частые Online/Offline-переключения, отдельная проблема
   «Нестабильный объект» и защита от лишних уведомлений.
3. **Maintenance mode.** Технические работы до заданного времени: проверки и история
   продолжаются, incidents и внешние notifications подавляются, выход автоматический.
4. **Multi-check SLA и история сервисов.** Отдельная доступность 1С, SSH, Web и других
   TargetCheck; доступность объекта остаётся по primary-проверке.
5. **SNMP interface alerts.** Неожиданный Link Down, flapping интерфейса,
   errors/discards и длительная высокая загрузка канала через существующий incident flow.
6. **Backup freshness / heartbeat monitoring.** Универсальный контроль последнего
    успешного запуска внешних задач, cron, 1С и backup.
Для каждого этапа переиспользуются Target Health, IncidentService, notifications и
scheduler; параллельные механизмы инцидентов не создаются. Обязательны проверка N+1 и
нагрузки scheduler, а также desktop/tablet/mobile. После этапа запускаются Ruff, smoke
и тесты затронутых модулей; полный pytest — только перед/после релизной сборки либо по
явной команде пользователя.

## Будущее развитие — схема устройств и большой экран

Реализовано по отдельной команде: read-only `/wallboard` для viewer/admin с TV-схемой
площадок, центральной крупной схемой, мини-схемами остальных площадок, общей сводкой и
лентой открытий/восстановлений incidents. Администратор расставляет встроенные SVG-значки
объектов на нейтральной сетке площадки; это не карта сети и не редактор топологии.
На конкретном TV-экране выбранные площадки можно пропорционально перераспределять
перетаскиванием угла блока; размеры сохраняются локально в браузере и сбрасываются
одной кнопкой без изменения серверной схемы площадки.
Плавающее окно событий можно перемещать, масштабировать, закрывать и возвращать
в исходное положение средствами самого TV-экрана.
Wallboard развивает только визуальное представление сохранённых схем: он использует
существующие Target Health и incidents для компактных сводок площадок, не рисует
топологические связи и не вводит унифицированные технические метрики под объектами.
Дополнительные сервисы объекта показываются небольшими кружками: на TV-экране их цвет
берётся из уже рассчитанного Target Health, а в редакторе схемы виден состав настроенных
сервисов. Основная проверка не дублируется такими индикаторами.
Визуальный стиль Wallboard допускает локальный cyberpunk/HUD-слой: холодные контуры и
очень медленная анимация сетки не меняют семантику цветов, схему, polling или обычные
страницы приложения. Верхняя HUD-телеметрия повторно использует уже рассчитанный
`portal_dashboard()` — без отдельного опроса, scheduler или хранилища. Перед его
включением создана контрольная точка состояния проекта.
Критические состояния отображаются визуальными карточками как на TV-экране, так и на
обычной странице «Состояние»: оба представления используют тот же пакетно вычисленный
Target Health, не создают incidents и не запускают проверки.
Во внутреннем чате можно упомянуть объект через `@`: выбранное из локального списка
упоминание ведёт на страницу «Состояние» к нужному объекту. Ссылка хранит его стабильный
идентификатор внутри сообщения, но в UI и Push отображается только человеческое имя.

Дальнейшее развитие — только по отдельной явной команде пользователя:

- без превращения в сложный графический редактор топологии.

## Долгосрочно — только по отдельной команде

- SMS через адаптацию имеющегося механизма 1С;
- теги объектов;
- филиальные коллекторы;
- Windows-агенты — в самом конце.

## Не планировать автоматически

- исключения по отдельным датам в рабочих графиках;
- отдельные получатели уведомлений по площадкам.
