# Самоконтроль сервера портала

## Решение

В ветке `0.8.x` блок «Сервер портала» на главной используется как компактная панель
здоровья самого Monitoring Maxval.

Постоянно видимая часть должна оставаться небольшой: состояние системы, размер очереди
проверок, число задержанных проверок, максимальное ожидание и запас scheduler, плюс уже
существующие CPU, память, диск и сеть. Расширенная статистика скрывается в стандартном
раскрываемом блоке «Подробности системы».

Runtime-метрики очереди собирает сам встроенный scheduler в памяти. Главная читает готовый
snapshot и не повторяет запрос определения due targets. Это сохраняет диагностический
экран дешёвым даже тогда, когда система находится под нагрузкой.

Задержка очереди считается относительно времени, когда объект должен был быть проверен.
Отдельно выделяется пропуск полного интервала объекта. Запас scheduler рассчитывается по
длительности последней пачки относительно самого короткого интервала участвовавших в ней
объектов с учётом шага scheduler.

Подробности дополнительно показывают rolling-статистику за 5 минут, среднее и P95 времени
полного задания проверки, параллелизм, количество активных объектов и объём текущей SNMP-
нагрузки. Размер PostgreSQL определяется через `pg_database_size(current_database())`; рядом показывается
текущее число подключений относительно `max_connections`. На других СУБД эти показатели могут
быть недоступны.

Самоконтроль на этом этапе является только диагностикой UI. Он не создаёт собственные
инциденты и уведомления и не изменяет расписание проверок автоматически.

Список SNMP-ошибок показывает до восьми включённых объектов и уже сохранённую безопасную
причину последнего SNMP polling с переходом к странице объекта. Scheduler хранит в rolling
window только время и тип необработанного исключения; его исходный текст не выводится в UI,
чтобы не раскрывать потенциально чувствительные данные. Полный trace остаётся в журнале
контейнера `app`.
