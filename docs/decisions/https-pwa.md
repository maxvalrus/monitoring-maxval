# HTTPS и PWA для ветки 0.7.x

- Статус: принято
- Дата: 2026-08-23

## Контекст

Портал уже работает по HTTP во внутренней сети и содержит базовые PWA-файлы.
Для ветки 0.7.x требуется добавить опциональный HTTPS и довести PWA до устойчивой
установки, не меняя штатный сценарий чистой установки и не расширяя продукт новыми
самостоятельными функциями.

## Принятые требования

1. После чистой установки HTTP остаётся режимом по умолчанию.
2. HTTPS является опциональным режимом, который администратор включает через
   настройки приложения.
3. Переключение HTTP → HTTPS и HTTPS → HTTP обратимо без переустановки приложения
   и без потери работоспособности.
4. Портал прежде всего предназначен для внутренней сети; публикация в интернет не
   является обязательным условием архитектуры.
5. Let's Encrypt/ACME не обязателен. HTTPS должен поддерживать собственные,
   self-signed и корпоративные сертификаты для закрытой сети.
6. Существующий HTTP-режим нельзя ломать ради HTTPS или PWA.
7. Ветка 0.7.x ограничена HTTPS, PWA и небольшими исправлениями существующих
   ошибок или интерфейса. Новые самостоятельные функции в неё не входят.
8. PWA в 0.7.x включает manifest, иконки, service worker и безопасный базовый
   offline cache. Push-уведомления не входят в задачу 0.7.x.
9. Для стабильной установки PWA необходимы PNG-иконки `192×192` и `512×512` в
   дополнение к существующему SVG.

## Решение

- Caddy является отдельным TLS reverse proxy. Основное приложение продолжает
  работать по HTTP только во внутренней Docker-сети и не получает Docker socket.
- HTTP остаётся режимом чистой установки и доступен параллельно с HTTPS. HTTPS и
  перенаправление HTTP → HTTPS — отдельные настройки; redirect доступен только при
  включённом и проверенном HTTPS и использует временный статус `307`.
- Если срок активного сертификата истёк или составляет не более двух суток,
  автоматический предохранитель отключает только HTTP → HTTPS redirect. Это сохраняет
  прямой HTTP-доступ для загрузки новой TLS-пары без отключения HTTPS вручную.
  Проверка выполняется при старте приложения и затем раз в час.
- HSTS, обязательный Let's Encrypt/ACME и автоматическое обновление сертификатов в
  0.7.0 не реализуются.
- Сертификат и приватный ключ хранятся вне БД в `tls/fullchain.pem` и
  `tls/privkey.pem` (на сервере: `/opt/monitoring-maxval/tls/`). Ключ не выводится в
  интерфейс и не записывается в журнал.
- Изолированный TLS-manager принимает только сертификат и ключ, создаёт candidate,
  проверяет PEM, ключ, соответствие пары, срок сертификата и `caddy validate`. Только
  затем candidate становится active; последняя рабочая пара сохраняется для rollback.
  Ошибка проверки не меняет рабочую конфигурацию, HTTPS или HTTP.
- После успешной проверки TLS-manager применяет уже валидированную конфигурацию через
  внутренний Docker Admin API Caddy. Этот API не публикуется на хост и доступен только
  TLS-manager; приложение к нему не обращается. Такой reload не зависит от файлового
  watcher Caddy. Если PEM-файлы заменяются по тем же путям, запрос reload содержит
  `Cache-Control: must-revalidate`, поэтому Caddy повторно загружает сертификат.
  Это сохраняет возможность вернуть предыдущую рабочую конфигурацию при ошибке
  применения.
- Caddy передаёт forwarded headers только внутри закрытой Docker-сети; приложение не
  публикует свой порт напрямую и включает proxy-header handling только в этом контуре.
- PWA кэширует только статические presentation-ресурсы и offline-страницу. Закрытый
  HTML, мониторинговые данные и приватные API-ответы не кэшируются и при отсутствии
  сети не выдаются как актуальные.

## Последствия

Реализация должна сохранять отдельный работоспособный HTTP-сценарий и проверять
полный цикл HTTP → HTTPS → HTTP, включая невалидный candidate и rollback.
