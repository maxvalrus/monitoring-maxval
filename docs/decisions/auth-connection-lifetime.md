# Освобождение соединения после авторизации

## Причина

При расследовании недоступности приложения после обновления TV обнаружены
`QueuePool limit of size 5 overflow 10 reached`, 15 соединений PostgreSQL в
`idle in transaction` после SELECT пользовательской сессии и очереди GET `/wallboard`.
При прекращении потока запросов приложение могло восстановиться без перезапуска.

Синхронная dependency `require_user` занимала соединение и возвращалась, оставляя
транзакцию открытой. Затем FastAPI отдельно ожидал поток для обработчика страницы.
Другие dependencies, ожидающие свободного соединения, могли занять весь AnyIO pool:
обработчики, которые завершили бы транзакции, не получали поток. Перезапуск только
временно снимал накопленную очередь.

## Исправление

`require_user` завершает транзакцию успешной авторизации перед возвратом AuthContext.
Это освобождает соединение до постановки обработчика страницы в очередь.
Следующая транзакция начинается при реальной работе обработчика с БД.

Рабочий SessionLocal использует `expire_on_commit=False`: User и UserSession остаются
загруженными и attached. Поэтому существующие изменения Push-предпочтений через
`auth.user` продолжают сохраняться. Правила авторизации, CSRF, ролей, истечения сессий,
обновления last_seen и обработчики страниц не меняются. Размеры пулов, scheduler,
схема БД, версия и дизайн не меняются.

## Регрессия

`tests/test_web_concurrency.py`:

- после авторизации соединение возвращено в pool, модели остаются attached;
- редактирование Push-предпочтения через AuthContext сохраняется;
- 24 параллельных запроса, 4 AnyIO workers, 2 DB connections без overflow;
- отдельно проверяется минимальный endpoint и фактический `/wallboard`;
- после завершения запросов нет занятых соединений.

На прежнем коде тест незавершённой транзакции и burst-тест падали: часть запросов
получала HTTP 500. После исправления оба сценария, включая фактический wallboard,
проходят. Проверка включена в smoke и профиль auth.

Предыдущая гипотеза о старых TV-вкладках объясняла возможный источник повышенной
нагрузки, но не устраняла серверную причину. Одного обновления JavaScript недостаточно.
Оригинал dependency сохранён локально в `backups/checkpoints/before-auth-pool-fix/`.

## Проверки после исправления

- Auth: 29 passed; web: 43 passed; communication: 55 passed; smoke: 36 passed.
  Профили пересекаются, результаты не суммируются как уникальные тесты.
- Ruff и compileall `src` проходят; полный pytest не запускался согласно правилу
  профилей разработки.
- Рабочий app пересобран и пересоздан без удаления volumes. Контрольные GET
  `/health/ready`, `/login`, `/static/wallboard.css` возвращают HTTP 200.
- После обновления PostgreSQL показывает свободные idle-соединения, без прежних
  15 idle-in-transaction сессий; новых QueuePool/HTTP 500 в контрольном окне нет.
