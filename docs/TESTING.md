# Стратегия тестирования Monitoring Maxval

Цель — сохранять полную регрессионную защиту, но не запускать весь набор после каждой мелкой правки.
Количество тестов само по себе не ограничивается: важны отсутствие дублей, скорость и покрытие критичных сценариев.

## Профили

### Smoke

Запускается после небольшой правки и перед переходом к следующей задаче:

```bash
python scripts/test_suite.py smoke
```

Smoke использует существующие тесты и не создаёт их копий. В него входят критические сценарии запуска,
аутентификации, мониторинга, отчётов, резервного копирования и коммуникаций.

### Тесты затронутого модуля

Во время разработки запускается только группа, которую меняли:

```bash
python scripts/test_suite.py module auth
python scripts/test_suite.py module checks
python scripts/test_suite.py module monitoring
python scripts/test_suite.py module snmp
python scripts/test_suite.py module reports
python scripts/test_suite.py module backups
python scripts/test_suite.py module communication
python scripts/test_suite.py module https
python scripts/test_suite.py module web
python scripts/test_suite.py module ui
python scripts/test_suite.py module release
```

Если изменение затрагивает несколько подсистем, запускаются все соответствующие группы.

### Полная регрессия

Полный набор не запускается по умолчанию после обычной задачи. Его запускают только
перед созданием релизного ZIP, после упаковки на распакованной копии архива или по
явной команде пользователя:

```bash
python scripts/test_suite.py full
```

После упаковки ZIP архив распаковывается в отдельный чистый каталог, и на его содержимом повторно
запускается полный набор. Только после этого архив считается прошедшим автоматическую регрессию.

## Правила добавления тестов

1. Новый тест добавляется только для нового поведения, критичного сценария или реально найденной регрессии.
2. Не создавать новый тест только ради номера релиза, если существующий тест уже проверяет тот же контракт.
3. Повторяющуюся подготовку данных выносить в fixtures/вспомогательные функции.
4. Однотипные сценарии объединять параметризацией, когда это улучшает читаемость и не скрывает причину сбоя.
5. CSS/HTML-проверки группировать по компоненту; не создавать отдельный тест на каждую мелкую декларацию.
6. Старый регрессионный тест не удаляется только из-за возраста. Его удаляют, если доказано, что он полностью
   дублируется другим тестом или проверяет уже удалённое поведение.
7. Тестовые файлы называются по функциональным областям. Номер релиза не используется
   как структура набора; регрессия сохраняется в соответствующем модуле.
8. Искусственного ограничения вида «не больше N тестов» нет.

## Релизное правило

Последовательность обязательна:

1. разработка — `smoke` + тесты изменяемого модуля;
2. перед сборкой — `full`;
3. после упаковки — `full` на распакованном финальном ZIP;
4. UI дополнительно проверяется визуально на desktop/tablet/mobile, потому что pytest не заменяет проверку вёрстки.
5. Оба типа `.mxbak` перед якорным релизом загружаются через штатную форму и
   восстанавливаются в отдельную PostgreSQL; рабочая база для этой проверки не используется.
